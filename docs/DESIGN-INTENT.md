## 1. 一句话

**把抽烟、喝酒、熬夜、久坐这些每天都在发生的小事，换算成「今天从你身上拿走了多少时间」，记在一本账上。**

首屏那行字就是产品名：**「今天，从你这里拿走的时间」**。下面是一个数字，记一笔之后它变成 `20 分钟`，再下面一行小字说「大约等于 一集短剧」。

---

## 2. 起点：一个很具体的烦躁

不是从「健康管理市场很大」开始的。是从一句我听了无数遍、但毫无感觉的话开始的：

> 「每天一包烟，少活十年。」

我知道它大概是真的。但它不构成任何行动。

原因不在于信息不够，而在于**尺度和我的经验对不上**。「十年」在时间上是抽象的，在概率上是群体的，在责任上是遥远的。它既不能让我今天少抽一根，也不能让我在抽完之后有半点具体的感受。

健康类产品给不出这个感受，是因为它们都选了同一个方向：**告诉你哪里坏了**。

- 有的给一个分数（`健康指数 72`）——我不知道 72 分和 68 分差在哪，也不知道它凭什么这么算。
- 有的画一个红点（`你的肝：⚠️`）——这是恐吓，恐吓的有效期只有三天。
- 有的给体检式报告（`肺功能下降 12%`）——我没有基线，也无从验证。

这些做法的共同点是：**它们都在描述一个状态，而不是在结算一笔交易。**

---

## 3. 关键转折：从「告诉你哪坏了」到「用时间结账」

第一版做的是最直觉的那件事：选一个行为 → 在人体上点亮相关器官 → 讲这个器官受什么影响。

做完之后我看了一遍，发现一个问题：**它是个解释器，不是个产品。**

用户点完「抽烟」，看到肺、心、脑、口腔一起亮起来，读了三段有出处的话，然后呢？他会觉得「哦，有道理」，然后关掉页面。这个体验没有留下任何东西——没有进度感、没有累积感、没有「我今天做了什么」的感觉。

于是换了机制。现在是这样：

```
一条行为  →  折算成一个分钟数（负数＝损耗）
今天所有条目  →  相加  →  今天从你这里拿走的时间
同一个权重  →  换一个时间尺度  →  如果一直这样，1 周 / 1 个月 / 1 年
```

为什么是时间：

1. **时间是所有人都有刻度的量。** 你有 24 小时，你花掉它们，你也浪费它们。不需要学习就能理解。
2. **时间是唯一能同时对上「一次」和「一辈子」的单位。** 一根烟 20 分钟，一包 400 分钟，一年 146000 分钟 ≈ 101 天。同一把尺子，从行为量到人生。
3. **时间是可比较的。** 一杯酒 15 分钟、一小时屏幕 21.8 分钟、一小时睡眠不足 11 分钟——它们能放在同一栏里排队，而「肝受到的损伤」和「肺受到的损伤」不能。
4. **数字是负的，但产品不悲惨。** 账本是正的还是负的，用户自己填。系统不评价，只结算。

**做的过程中砍掉过的东西：**

| 砍掉的 | 原因 |
| --- | --- |
| 身体年龄（`你的身体年龄：34 岁`） | 做过一版，砍了。它不是可验证的量，且一旦给出，用户会追问「那我还能活多久」——那是另一个问题，且不可回答 |
| 健康总分（`综合负荷 61/100`） | 把抽烟的害和运动的益压成一个数，等于替用户做了他没有授权的价值判断 |
| 损伤百分比、病理解剖图 | 输入只有「每天几支」，输出一张黑肺，是伪造精度 |
| 步数式打卡 | 会把注意力从「账」转移到「连胜」，产品变成游戏 |

## 4. 三条数字铁律

这个产品的分数里有一半靠「不把推测表现成已测量的事实」。所以数值层定了三条规则，**写在代码里，不是写在文档里**：

### 4.1 有数字，就必须有 caveat

`data/weights.js` 里有一个 `validate()`，逐条检查数据：来源是否登记、证据等级是否合法、**有数字却缺 caveat 的条目直接记为问题**。

```js
if (typeof item.minutes === 'number' && !item.caveat) {
  problems.push(id + '：有数字但缺限制说明');
}
```

它不是运行时抛错，而是由测试守门——`tests/ledger.test.cjs` 里有两条断言要求 `validate()` 返回**空数组**：

```js
assert.deepStrictEqual(W.validate(), []);
```

也就是说，谁想加一个没有说明的数字，他会先看到测试红。这是刻意的选择：错误挡在提交前，而不是挡在用户面前。

### 4.2 推算出来的数，必须标明是推算的，而且写明推算路径

睡眠那一项最能说明问题。原文研究给的是「20–24 岁人群寿命损失约 0.94 年」，**没有**给「每少睡一小时等于多少分钟」。这个 11 分钟是我算的：

```
0.94 年 ÷ 60 年 ≈ 每天 22 分钟 ÷ 2 小时缺口 = 每小时 11 分钟（区间 5–17）
```

所以界面上这一项旁边有小灰字 `推算值 · 长期少睡才成立`，点开是完整路径 + 三个前提（只长期成立 / 睡眠与死亡率是 U 型 / 原研究为观察性未证因果）。

**原文给的数和折算出来的数，不是一回事。** 不能让用户以为是研究结论。

### 4.3 只在推演尺度内成立的数，才允许进推演

推演卡最长看 1 年。睡眠那个 11 分钟是「一辈子」摊出来的，放进 1 年的推演里，等于把一辈子的代价说成一年的代价——虽然数字一样，含义差两个数量级。

所以 `forecast.js` 里有一份白名单：

```js
const ELIGIBLE = ['smoke', 'alcohol', 'sit'];
```

睡眠**有数字也不进**。同样被挡在外面的还有含糖饮料、快走——方向可信，但没有折算口径。

> 判断标准：**推演里出现一个编出来的数字，比不出现更糟。**

## 5. 三个刻意的「不做」

### 5.1 不抵消

抽烟 + 运动，心肺部位会同时出现「不利」和「有益」两条结论，**分别显示，不合成净值**。

理由：净值的算法本身就是一个价值判断（一根烟等于几分钟快走？），而这个判断我没有依据做。更实际的问题是——一旦有了净值，用户会开始「用运动换烟抽」，这是产品不该暗示的行为。

### 5.2 不猜

资料库里没有的行为，就明确说「当前未收录对应结论」，**绝不说「无害」**。

同理，某个器官没有当前行为的资料时，写「当前未收录」，不写「暂无影响」。「没有数据」和「没有影响」是两件事，混在一起就是在骗人。

### 5.3 不插值

「每天 1 支」和「每天 2 支」不是两倍关系。

UI 上给你几个按钮（1 / 2 / 5 / 10 / 20 支），每个按钮对应的是**研究里讨论过的暴露条件**，不是在一条直线上取点。用户选了 2 支，系统累加两次「每支 20 分钟」，但**不会**因此宣称「2 支的肺癌风险是 1 支的两倍」——那是另一个量，没有资料支持。

## 6. 视觉：为什么是浅色的

这条最反直觉，写出来是因为它被推翻过一次。

第一版是深色科幻风：深蓝黑底、青蓝光效、透明面板、扫描网格。理由很充分——看着像医疗设备，出片好看，符合「生命科学工作台」的直觉。

**后来全换成浅色：米白底 + 墨绿字 + 松绿主色 + 陶土橙强调。**

真正的理由不是审美，是**可信度**：

- 深色 + 发光 = 科幻感 = **暗示这是某种检测设备**。但这个东西没有检测任何东西，它是在算账。发光的效果在替产品承诺它做不到的事。
- 账本应该是纸的颜色。你会信任一个用黑字写在米白纸上、旁边留白的账本，不会信任一个在黑色屏幕上发蓝光的账本。
- 色彩只担三个职责：松绿 = 可交互，陶土橙 = 不利影响，其余全部让给黑白灰。**用色克制本身就是可信度。**

（诚实记录反对意见：深色在截图和视频里更抓眼。这条定的是「产品该用浅色」，将来为了展示另做一套深色截图，不算推翻。）

## 7. 技术：为什么死活不上框架

原生 HTML/CSS/JS，零运行时依赖，没有 `npm install`，没有构建步骤。

这不是「复古」或「炫技」，是被两条验收指标锁死的：

| 指标 | 内容 | 换框架的后果 |
| --- | --- | --- |
| AC-24 | 断网可用 | Vite/Next 产物依赖 dev server 或 hash 路由，演示现场断网就废 |
| AC-28 | 十分钟内跑起来 | 需要 `npm install` + 版本对齐，在别人的电脑上跑不起来是常态 |

所以规则是：**任何人 clone 下来，`node scripts/serve.cjs`，浏览器打开 `127.0.0.1:4173`，就能用。** 不需要装包、不需要联网、不需要密钥。

代价我也清楚：没有类型、没有组件化、状态管理靠手写。69 次提交里有相当一部分是在还这个债。但换来的「任何人都能一分钟跑起来」是比赛评分里「过程可复现 25%」的抓手，我认为值。

**唯一例外：AI 解读。** 服务端一个极小代理脚本调大模型，Key 不进浏览器。没网或没 Key 时自动退回本地规则文案，功能不缺——所以它没有破坏上面两条。

## 8. 我自己知道有问题、但没定下来的地方

**这是我最想听意见的部分。** 下面每条都是真问题，不是客套。

### 8.1 「时间损耗」这个隐喻，可能经不起追问

我用「从你这里拿走的时间」作为核心隐喻。它好懂、有冲击力，但它有一个隐患：**它把「健康风险」简化成了「寿命长度」**。

抽烟 20 分钟/支这个数字，来自人群平均寿命统计。它不意味着「你今天抽了这根烟，就少活了 20 分钟」——它意味着「一个长期每天抽这么多的人，平均少活这么久，摊到每支上是 20 分钟」。

界面上的 caveat 写了这一点，但**用户会不会读，我控制不了**。如果他只记住「我这根烟值 20 分钟」，那这个产品就变成了一个精致的概率误读器。

我一直没想清楚：是继续用这个隐喻（好懂但有风险），还是换一个更准确但更弱的说法（准确但没人记得住）。

### 8.2 账本是「今天的」，但健康是「长期的」

现在的设计是日账：今天记了几笔，今天拿走多少分钟。零点清零。

问题是：**行为和后果的时间尺度不匹配。** 一根烟的风险是几十年累积的，一天的账显示 20 分钟，两者的量级差了四个数量级。推演卡想补这个缺口（1 周 / 1 个月 / 1 年），但它只是个附加模块，不是主叙事。

用户会不会觉得「反正明天清零，今天记多少都无所谓」？我不知道。这是设计上最大的不确定性。

### 8.3 器官图该画几个：删减和「只删一半」

数据层登记 10 个器官，人体上画了 10 个，能点 **9 个**（正面 7 个：大脑、眼睛、口腔、肺、心、肝、肠道；肾与脊柱在背面视图）。只有「胃」不出现——它在 30 条行为里一条关联都没有，点开是空的。

**这里踩过一个必须写下来的坑。** 10 月 21 日为了让人脸干净，我把眼睛从人体 SVG 上删掉了，但忘了数据层还连着 5 条用眼行为，以及「屏幕时间」的器官落点。结果：

- 文字层照数据说「涉及 心脏 · 眼睛」
- 人体上只有心脏亮，眼睛根本不存在
- 全程不报错——因为我另外写了一道防御，把画不出来的器官从**可点列表**里滤掉了，看起来像「这个产品本来就没有眼睛」

**修的地方只堵了一半，漏的地方继续漏。** 这不是「删减的取舍」，是删得不彻底。10 月 24 日补回来了（画一个极简眼区，不是画一张脸），并加了一条跨层校验用例：数据层引用到的每个器官，人体图上必须有节点，否则测试直接红。

原来的判断「没有关联就不画」本身没错，错在**只画了一半的账**——视觉删了，数据没跟着走。

### 8.4 30 条行为里，只有 3 条能进推演

`smoke / alcohol / sit` 三条有「在 1 年内成立」的折算口径，其余 27 条只有定性说明。

这意味着推演卡实际上只能反映用户账簿里的一小部分。如果一个用户今天记的是「熬夜 + 外卖 + 没运动」，推演卡会显示「暂无」——**看起来像功能坏了**。

目前没有好的解法。要么放宽标准（编数字，违反铁律 4.3），要么改文案说明为什么没有（啰嗦），要么隐藏推演卡（等于承认这个功能只对抽烟喝酒的人有用）。

### 8.5 我在自己给自己做裁判

这个产品从 PRD 到视觉到数值全是我一个人做的，数据口径也是我自己定的（哪些研究能进、能进到什么程度、怎么折算）。

评审的时候，我无法证明我没有为了让数字更「好看」而挑选来源。我只能把筛选过程写下来供人核对（`docs/prompt-log/` 下有 4 条完整的取舍链，含用户原话和我的错误判断）。但**这仍然不是独立验证**。

### 8.6 移动端没做完

桌面端调了很多轮。移动端目前只验证过 375px 下不横向溢出，**没有在真机上跑过完整流程**。这是已知的缺口，不是「暂未测试」。

### 8.7 最重要的那个数字，出处反而不完整

矛盾的地方在这里：整个产品最核心的数字是「每支烟 20 分钟」，而这条来源 `ucl-cigarette-2024` 在数据文件里的登记是——

> 机构 UCL ／ 标题《The price of a cigarette: 20 minutes of life?》／ 期刊 Addiction ／ 2024-12-29 ／ 人群：英国医生研究与百万女性研究 ／ **DOI 与原文链接待补**

也就是说：**其它 11 条科普来源都有 URL，唯独这条期刊来源没有 DOI。**

不是没查，是当时没查到就先把数据放进去了，然后在 `note` 里如实写「待补」。这个处理方式本身可以批评——按 `data/weights.js` 文件头自己定的第 5 条（「宁可不给数字，也不给一个找不到出处的数字」），它其实该被拦下。

我把它留在这里，是因为我知道这是个真问题，而不是我看漏了。

## 9. 我希望你怎么评

按优先级：

1. **第 8.1 条（时间隐喻的风险）** 你怎么看？如果是你，会换掉它吗？换什么？
2. **第 8.2 条（日账 vs 长期健康）** 这个错配是不是致命伤？有没有产品用别的方式解决了这个问题？
3. **有没有哪一条「刻意不做」其实是懦弱？** 比如「不抵消」「不插值」，我称之为原则，但也可能是回避矛盾。
4. **如果这是你评审的一个参赛作品，你会扣分扣在哪里？** 请直说，不要顾及面子。
5. 有没有明显的事实性错误、逻辑不自洽，或者我应该知道但明显不知道的东西？

**不需要评的**：视觉精修建议（已定稿）、技术栈建议（被验收指标锁死）、功能增加建议（10/31 截止，不做新功能）。
