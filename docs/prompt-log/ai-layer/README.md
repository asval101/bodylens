# 解读层：从「一段话」到「三段式」

- 日期：2026-10-20
- 对应提交：`68010a3`（解读层）、`67c52f4`（服务端）
- 验证：`npm test` 48 项通过（本轮新增 13 项）；端到端流式脚本 7 个分块正常

## 1. 初始意图（用户 Prompt 原文）

> 所有以前的文件，你如果觉得不合适就可以提出更改，那些只是参考，我觉得也可以把那些器官做成卡通3D的样子，你觉得吗，或者之后再讨论这个问题，现在解决ai和服务器的问题

前一轮的补充：

> 选b 买那个服务器够吗，我还想再加一些动画，比如点击每一个器官都会有相应的动画，还有就是服务器跟域名都要买还是，买域名两个有什么区别

## 2. 我对需求的第一判断

用户说「现在解决 AI 和服务器」，但这两件事在代码里其实是同一件事：
**AI 要能调通，前提是有一个能保管密钥的服务端；服务端要能部署，前提是不能有 npm 依赖。**

所以顺序不能反过来。我先定了两条硬约束才动手：

1. 服务端零依赖。装了 `express` 就多一步 `npm install`，`AC-28 十分钟启动`当场变脆。
2. 解读层必须有本地版本。否则「断网可用」（AC-24）从「降级」变成「失效」，而这两条正是复现分 25 的抓手。

## 3. 第一轮：写出能跑的版本，但文案是一堵墙

`interpret.js` 第一版把所有内容拼成一个 `detail` 字符串：变化句 + 归因句 + 三条细则（额度 / 区间 / 无口径）+ 一句建议。测试全过。

截图之后问题立刻出现：

- 正文变成 6 句话挤在 3 行里，读者会直接跳过
- 建议句混在描述里，读起来像在说教
- 「结论」和「细则」在视觉上是同一层，没有主次

**这里暴露的是一个测试测不出来的缺陷**：断言只检查了「文案里有没有这个信息」，没检查「读起来是不是一团」。纯文本测试对排版质量是盲的。

## 4. 人工纠偏

措施一：把返回值从 `{ headline, detail }` 拆成 `{ headline, detail, hint }`。

- `headline` 只陈述数字，由账本算，模型无权改写
- `detail` 解释这些数字怎么来的、哪些没折
- `hint` 一句可以试的动作，单独成段，左侧一条细线

措施二：把 `caveats()` 从「三类情况各说一句」压到「两句以内」。

原来写：

```
酒精还在本周额度以内，所以没有计入分钟——那是研究成立的剂量条件，不是给它开后门。
屏幕时间的原始区间很宽，这一项只能当量级看，不能当刻度。
睡眠不足没有公开的折算口径，只记下发生，不折分钟。
```

改成分号串联的一句加一句：

```
酒精没超本周额度，不计分钟（那是研究成立的剂量条件）；屏幕时间的原始区间太宽，只能当量级看。
睡眠不足 没有公开的折算口径，只记下发生。
```

**取舍说明**：信息一点没删，只是不再各占一句。三条并列的细则天然会被当成免责声明跳过，串成一句反而更容易被读完。

## 5. 第二轮：符号方向搞反了

测试 `对比昨天变多与变少的措辞不同` 失败，输出是：

```
比昨天少了 1 小时 20 分。  ← 实际上是多抽了 4 支
```

原因：账本里 `delta = 今天 - 昨天`，而分钟的收益在正、损耗在负。多损耗时 `delta` 是负数，我却写了 `if (d > 15) return '比昨天多了'`。

修正后约定写进注释：**`delta` 为正表示「比昨天好」，为负表示「比昨天差」**，变多时要把符号翻回来再取绝对值，否则会出现「比昨天多了 -80 分钟」。

## 6. 第三轮：额度内会输出「被拿走 0 分钟」

用户只喝了两杯，还在每周 12.5 杯的额度内，`totalMinutes` 就是 0。第一版直接命中 `total === 0` 的默认路径，输出：

```
今天被拿走 0 分钟。
```

这在产品上是灾难——它把「额度」讲成了「没事」。

修正：为 `total === 0 && counted > 0` 单开一条分支，输出「今天记了 N 项，都还在额度以内」，并在 detail 里说明额度是研究成立的剂量条件、每周重置。

## 7. 服务端：限流定得太紧，演示会自己把自己锁住

第一版限流 6 次/分钟。算了一下演示节奏：评委或录制时每两秒记一笔，一分钟就是 30 次，第 7 次开始 429。

更糟的是客户端把 429 当成「这台服务器没接上」，直接写进 `sessionStorage` 标记，**整场会话再也不请求 AI**。

两处一起改：

1. 服务端放宽到 12 次/分钟、800 次/日
2. 客户端区分错误类型：429 标 `temporary`，只退回本条，不清除会话可用状态；只有 404 / 5xx / 无密钥才算「没接上」

## 8. 第八轮：流式验证出现假阴性

第一次验证流式，代理日志是 `fetch failed`，假上游一个请求都没收到。

原因是假上游用 `&` 起在后台，**上一个 shell 退出时进程被回收了**，而 `curl` 拿到的是沙箱代理返回的 502，看起来像「上游拒绝」。

修正：写了一个同进程组的端到端脚本——假上游、子进程代理、真 fetch 三者在一个 node 进程里跑，跑完自己收尾。结果：

```
status = 200
content-type = text/event-stream; charset=utf-8
chunks = 7
text = 今天主要来自香烟，比昨天多了一小时。
```

**教训**：跨工具调用用 `&` 起的后台进程不可靠，验证类脚本必须自己持有生命周期，否则会为一个不存在的问题改代码。

## 9. 最终结果

- 首屏解读区三段式，标签区分「本地解读 / 正在读 / AI 解读」
- 断网、无密钥、超时、429 四种情况各自有明确降级路径，界面上都不弹错误
- 服务端零依赖，无密钥时 503，前端自动用本地解读
- 服务端只接收白名单数值字段并做长度裁剪，客户端无法构造提示词注入

## 10. 一句话复盘

这一轮真正的难点不是「把 AI 接上」，而是**想清楚 AI 失败时产品还剩什么**——本地规则不是降级方案，是地基；在线模型只负责让地基上的话说得更好听。
